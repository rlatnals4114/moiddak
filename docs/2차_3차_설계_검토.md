## C5. B모드(30분 시간표) 날짜 부담
- **현재(코드 확인)**: 약속 만들기에는 이미 ‘달력에서 여러 날짜 켜기 → 기본 시간 범위 → 고른 날짜 모두에 적용 → 날짜별 수정’이 있다. 응답 화면은 **하루씩** ‘오전/오후/저녁/하루 전체/구간 선택/이 날 모두 해제’만 있다.
- **제안(화면만)**: 응답 화면에 ‘여러 날 한 번에’ 패널 — 조사 날짜 체크(전체 선택 가능) + 시간 구간(시작~끝 또는 오전/오후/저녁) + `선택한 날짜에 가능으로 추가 / 해제` + 적용 전 ‘N일 × M칸’ 미리보기. 기존 선택은 유지되고, 주최자가 정한 칸 밖은 선택할 수 없음(지금처럼 서버 `submit_grid` 가 범위 검사).
- 예상 클릭 수(3일·18~22시 응답): 지금 3일×(날짜 선택+구간 2개+적용) ≈ 12번 → 개선 후 날짜 3 + 구간 2 + 적용 1 ≈ 6번(전체 선택이면 4번).
- 테스트: 단위(선택 계산) + 화면(375px) + 기존 modes 테스트.

## B4. 새 멤버의 약속 열람 범위
- **현재**: `group_overview` 가 모임방 **모든 약속의 제목·상태·날짜**를 멤버 전원에게 준다(가입 전 약속 포함). 상세·응답은 이미 참여자만.
- **제안**: `group_overview` 를 새 파일에서 교체 — 멤버에게는 **내가 참여자이거나 주최자인 약속만** 목록에 포함. 관리자는 지금처럼 전체(관리 목적).
- 영향: 지금 ‘참여하지 않는 약속’으로 제목만 보던 **기존 멤버**도 그 항목이 안 보이게 된다(결정서 “기존 멤버의 정당한 이력 접근 유지”와 충돌 여부 확인 필요 → 아래 질문 1).
- 테스트: 신규 멤버가 가입 전 약속 0건, 포함된 진행 중 약속만 보임, 관리자 전체 보임, 직접 테이블 조회 0행.

## B3. 일반 멤버도 초대 링크 공유 (관리자 통제)
- **현재(007)**: 공용 링크는 모임방당 1개, 관리자만 발급, 원문은 만든 기기에만.
- **제안(추가형)**
  - `groups` 에 `allow_member_invite boolean default true`, `capacity integer default 50 check (1..200)`.
  - 공용 링크를 **사람별로**: `group_join_links` 에 이미 있는 `created_by` 기준으로 ‘사람당 살아 있는 링크 1개’(유일 인덱스 교체: 모임방 → 모임방+발급자). 멤버는 `create_my_join_link` 로 **자기 링크**를 만들고(다른 기기에서도 새로 만들면 됨 → 원문 저장 불필요), 관리자는 `revoke_all_join_links`·`set_member_invite(on/off)`·`set_capacity`.
  - 가입 함수는 정원을 `groups.capacity` 로, 멤버 공유가 꺼지면 멤버가 만든 링크 거부.
  - **차단 해제**: 관리자가 뺀 사람(`removed_at`)은 재가입 불가 유지 + 관리자 전용 `unblock_member`. **스스로 나가기**는 지금 기능이 없음 → `leave_group`(본인) 추가 시 `removed_by_self` 표시로 재가입 허용.
  - 한계(화면에 안내): 익명 계정은 다른 브라우저에서 새 신원이 되므로 ‘차단’을 완전히 막을 수 없음.
- 테스트: 일반 멤버 링크 생성·가입, 공유 끄면 거부, 관리자 일괄 폐기, 정원, 차단·해제, 남의 링크·관리자 링크 노출 없음, 기존 개인 링크 정상.

## C2. 일회성 약속: 이름 미리 입력 없이 링크로 참여
- **현재**: `create_meeting_v2` 가 참가자 **2~12명 이름**을 요구, 각자 개인 초대 토큰.
- **제안(추가형)**
  - `create_meeting_open(p_title, p_my_name, p_mode, p_times, p_days)`: 주최자 1명만 참여자로 만들고(또는 주최자 미참석), 공용 참여 링크를 발급(`private.meeting_join_links`, 해시·만료·폐기 — 모임방 링크와 **별도 표·별도 토큰**).
  - `preview_meeting_join_link`(제목만) · `join_meeting_with_link(token, 이름)`: 명시적 참여 → `participants` 행 생성(같은 기기 재클릭은 기존 행 반환, 이름 중복 거부). 인원 상한 제안 30명(지금 12명 → 질문 2).
  - 화면: 만들기 1단계에서 명단 칸 제거(‘명단 미리 넣기’는 선택으로 남김), 관리 탭에 ‘초대 링크 복사/공유’, 집계는 **‘참여한 사람 n명 · 일정 응답 n/n’** — 링크를 받고 아직 안 들어온 사람은 알 수 없다고 안내.
  - 기존 명단형 약속·개인 링크는 변경 없음.
- 테스트: 이름 없이 생성, 미리보기 최소 정보, 명시적 참여, 재방문, A/B 응답, 남의 응답·관리 권한 불가, 기존 약속 회귀.

## B1. 참석 확인(RSVP)
- **현재**: 저장 칸 없음(화면은 ‘참석 여부 미확인’).
- **제안(추가형)**
  - `meetings.schedule_round integer default 1`(B2 와 공유, 확정이 바뀔 때마다 +1).
  - 새 표 `meeting_rsvps(meeting_id, participant_id, round, status check in ('yes','no','maybe'), updated_at)`, 유일 `(participant_id, round)`. 행이 없으면 **미응답**(미정과 구분).
  - `set_my_rsvp(meeting_id, status)`: 확정 일시가 있고 호출자가 그 약속 참여자일 때만, 현재 회차로 저장(본인만). RLS 읽기: 같은 약속 참여자·주최자.
  - 장소만 바뀌면 회차 그대로(응답 유지 + ‘장소가 바뀌었어요’ 안내), 날짜·시간이 바뀌면 회차 +1 → 전원 미응답, 이전 회차 응답은 이력으로 남음.
  - 화면: 확정 직후 ‘참석 여부 알려주기’, 주최자 `참석 n · 불참 n · 미정 n · 미응답 n`. 일정 투표 결과로 자동 ‘참석’ 처리하지 않음.
- 테스트: 4명 초대·1명 투표·0명 RSVP 표시, 4상태, 타인 수정 거부, 장소 변경 유지, 날짜 변경 재확인.

## B2. 확정 후 재조율(버전)
- **현재**: 확정 후 일정 표·응답이 잠기고(`status <> schedule_open` 이면 응답 거부), 회차 개념 없음.
- **제안(추가형이지만 범위가 큼)**
  - `meeting_rounds(meeting_id, round, selected_start, selected_end, confirmed_at, confirmed_by, reason, superseded_at)` — 확정 이력.
  - 회차별 후보·응답 분리: `time_options`, `schedule_submissions`, `availability_choices`, `schedule_survey_days`, `grid_availability` 에 `round integer default 1` 추가(기존 행은 1회차). 기본키·유일 제약에 회차 포함 → **기존 제약 교체가 필요**(데이터 삭제는 없음).
  - `start_reschedule`(주최자): 새 후보 + 사유 → `rescheduling = true`, 기존 확정은 ‘기존 확정 · 변경 검토 중’으로 유지(캘린더에서 안 사라짐). `cancel_reschedule` → 원상. 새 확정 → 회차 +1, RSVP 재확인(B1).
  - 기존 응답·확정 함수(`submit_schedule`, `submit_grid`, `confirm_schedule`, `confirm_grid`)의 **새 버전**이 필요(회차 인식). 이전 앱 버전과 동시에 쓰면 안 되므로 앱·DB 를 함께 배포.
- 위험: 일정 관련 표 5개와 함수 4개에 영향 → 별도 단계로, 스테이징(개발용 DB 분리) 권장.

## B6. 계정 연결·기기 복구
- **방식 제안**: Supabase 익명 사용자에 **이메일을 연결**(`updateUser({ email })` → 메일 인증)하면 **같은 사용자 ID 가 정식 계정**이 된다 → 모임방·약속·역할·캐릭터가 그대로 유지(병합 불필요). 다른 기기에서는 이메일 OTP 로그인 → 같은 ID.
- 충돌: 이미 다른 계정에 쓰인 이메일이면 연결 거부 + 안내(자동 병합 없음).
- 필요한 것(운영 설정, 승인 필요): Supabase Auth 이메일 사용·OTP 템플릿, **운영 메일 발송(SMTP)** — 기본 메일은 발송 수가 매우 적어 실제 서비스에 부족.
- 화면: 내 정보 ‘이 기기에서만 유지될 수 있어요 → 이메일로 계정 지키기’(선택), 로그인 없이도 응답 가능 유지.
- 테스트: 연결 후 다른 기기 로그인 시 내 데이터만, 관리자 권한 유지, 이미 쓰인 이메일 거부, 인증 없이 탈취 불가.

## B7. 테스트 데이터
- 지금 운영의 `[테스트] …` 모임방·약속은 **삭제하지 않음**. 제안: 시연용 1개만 남기고 나머지 모임방은 기존 ‘모임방 종료(archive)’로 목록에서 내리기, `[테스트] 운영 확인방` 공용 링크는 끄기 — **승인 후 화면에서 수동 실행**(DB 변경 없음).
