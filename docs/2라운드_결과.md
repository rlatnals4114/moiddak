- 모임방 ‘종료’(archive)는 `archived_at` 만 기록하는 **되돌릴 수 있는 동작**(삭제 아님). 종료하면 공용 링크 미리보기는 ‘종료된 모임방’, 가입은 거부, 기존 약속 주소는 그대로 열림.

## 4. B2 — 개발용 DB 와 버전 보존 방식(설계)
- **개발용 Supabase 프로젝트를 새로 만든다**(무료 플랜, 운영과 별도 URL·키). 001~011 을 순서대로 실행해 스키마만 복제하고, 데이터는 **자동 테스트가 만드는 가짜 데이터만** 쓴다(운영 데이터·비밀 키 복사 금지). dev Worker(`moiddak-dev`)는 이 DB 를 보도록 `config.js` 를 환경별로 분리(현재는 하나).
- 버전 보존: `meeting_rounds`(회차별 확정 일시·확정자·사유·대체 시각) + 일정 표 5개(`time_options`, `schedule_submissions`, `availability_choices`, `schedule_survey_days`, `grid_availability`)에 `round` 칸(기존 행=1). 기본키·유일 제약에 회차 포함 → 제약 교체 필요(데이터 삭제 없음). 응답·확정 함수 4개는 새 버전(회차 인식) — **앱과 DB 를 같이 바꿔야** 해서 운영 적용 위험이 크다.
- 재조율 중 표시: ‘기존 확정 일정 · 변경 검토 중’(캘린더에서 유지), 취소하면 원상, 새 확정 → 회차 +1 → B1 참석 확인 새로(011 트리거와 연결).
- 승인 필요: 개발용 프로젝트 생성(사용자 계정에서), 그 뒤 초안 작성·dev 검증 결과 보고 → 별도 운영 승인.

## 5. B6 — 인증·SMTP 요구사항과 위험(설계)
- 방식: 익명 사용자에 이메일 연결(`updateUser({ email })` + 메일 인증) → **같은 사용자 ID 가 정식 계정** → 모임방·약속·역할·캐릭터 그대로(병합 불필요). 다른 기기는 이메일 OTP 로그인.
- 위험: ① 이미 다른 계정에 쓰인 이메일 → 연결 거부(자동 병합 금지), 두 기기에서 따로 만든 익명 데이터는 합쳐지지 않음 ② 메일 발송: Supabase 기본 메일은 발송 수가 아주 적어 실서비스 불가 → 공급자·발신 도메인·SPF/DKIM 필요(아직 없음) ③ 인증 링크 만료·오발송 대응 ④ 로그인 화면이 ‘복구되는 것처럼’ 보이지 않게 — 연결한 사람만 복구된다고 정확히 안내.
- 지금 가능한 것: 설계·화면 문구 초안까지. 실제 인증은 SMTP 준비 + 승인 후.

## 6. B7 — 테스트 데이터·활성 링크 현황(실행 안 함)
- **정확한 전체 목록은 아직 조회하지 못함**: 관리자 키를 쓰지 않으므로 다른 익명 계정이 만든 데이터를 볼 수 없다. → `supabase/drafts/b7_inventory_READONLY.sql`(SELECT 만)을 SQL Editor 에서 실행하면 `[테스트]` 모임방·약속, 살아 있는 공용 링크 수, 테스트 아닌 데이터 수가 나온다.
- 이 세션에서 직접 확인한 활성 링크: `[테스트] 운영 확인방`(시연용 지정) — 화면 캡처 때 다시 만든 공용 링크 1개 활성(30일). dev 확인용 `[테스트] dev 공용초대` — 공용 링크 1개 활성. 자동 테스트(`group_join`, `qa_flow`)가 실행마다 `[테스트] 공용 초대방`·`[테스트] QA 흐름방` 을 만들고 링크를 남긴다(일부는 테스트 안에서 폐기).
- 제안(승인 후 실행): ① 시연·실기기 검증이 끝나면 `[테스트] 운영 확인방` 링크 끄기, 시연 직전 새 링크 → 시연 뒤 즉시 끄기 ② 나머지 `[테스트]` 모임방은 **종료(archive)** — 삭제 아님, 되돌릴 수 있음 ③ 자동 테스트가 끝날 때 자기가 만든 링크를 끄도록 테스트 코드 보강 ④ 장기적으로 테스트는 개발용 DB 로(4장).
